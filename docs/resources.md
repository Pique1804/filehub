# Ресурсы и границы проверки

Начальная конфигурация для небольшой установки: **2 vCPU, 2 ГБ RAM,
8–12 ГБ под Linux и приложение**. Объём оригиналов, миниатюр, OCR и индекса
нужно учитывать отдельно. Это ориентир для теста, не измеренный минимум
для большой библиотеки. Количество файлов и обработка видео влияют на нагрузку.

В конфигурации варианта без сборки заданы пределы:

| Компонент | Лимит памяти | Лимит CPU |
| --- | --- | --- |
| Filehub вместе с Python-обёрткой и дочерними обработчиками | 768 МиБ | 1 ядро |
| Входной Nginx | 96 МиБ | 25% ядра |
| Необязательный сервис дисков на хосте | 96 МиБ | 25% ядра |

В полном режиме сервис дисков устанавливается автоматически; `--folders-only`
явно оставляет только работу с папками. Установка готовых Debian/Ubuntu-пакетов
ограничена отдельной группой 384 МиБ/50% CPU и не компилирует приложение.

Лимит — потолок процесса, а не обещание такого потребления. Для ОС и соседних
служб нужен запас. Превышение лимита останавливает соответствующий сервис;
это не гарантия от любой проблемы с ресурсами хоста. Общий лимит контейнера
и реальные измерения остаются обязательной частью отдельной проверки установки.

В одном из тестов Debian 12 в LXC использовались 2 vCPU, 2 ГиБ RAM
и 12 ГиБ под системный диск.
До создания аккаунта Python-мастер занимает около 13 МиБ, Nginx около 2 МиБ.
Во время сквозной проверки с маленькой проверочной библиотекой группа
Python/Go занимала около 207 МиБ, включая учитываемый cgroup файловый кэш.
Это единичное измерение, не минимум для реальной библиотеки.
После настоящего mount, загрузки PNG и перезагрузки LXC хостовый сервис занимал
около 12 МиБ, его пик — около 14 МиБ. Все тестовые диски и файлы отдельные;
личная библиотека в эти цифры не входит.

Python-тесты модели запускались
с пределами 256 МиБ/50% CPU, отдельный headless-браузер — 512 МиБ/50% CPU,
без swap в этих группах. Тесты используют небольшие синтетические папки,
поддельные команды монтирования и имитацию bootstrap Go. Дополнительно выполнена
сквозная проверка настоящего опубликованного Go и Nginx с загрузкой PNG и
созданием миниатюры. Эти проверки не измеряют потребление при индексации
домашней библиотеки и реальном копировании видео.

Выпуск 1.40.1 собран на тестовом хосте Windows.
Все процессы одной сборки ограничены Windows Job Object: суммарно 6 ГиБ памяти
и 25% общего процессорного времени. Go и Android собирались последовательно.
Android с первым заполнением кэша занял около 10 минут. Это измерение одной
машины, не минимальные требования к сборке. Обычная установка сборок не запускает.
Готовые Linux-тесты выполнялись в тестовом LXC с лимитом 768 МиБ; браузер — в отдельной
группе 512 МиБ. [Результаты выпуска](release-verification-1.40.1.md).

## Замер на синтетической библиотеке

21 ноября 2026 проверили сборку `1544d40` на Debian 12 x86-64 в Windows VM.
В тесте было 12 000 JPEG размером 640×360 и 3 000 обычных файлов. Сервер
работал с `GOMAXPROCS=2`, клиент обращался к нему по localhost.

| Замер | Результат |
| --- | --- |
| Холодный запуск и индексация 15 014 записей | 4,45 с |
| Поиск 3 000 совпадений с выдачей первых 300, медиана 7 запросов | 0,42 с |
| Открытие папки с 3 000 файлами, медиана 7 запросов API | 0,26 с |
| Первая страница из 240 фото, затем медиана следующей страницы | 1,22 с и 1,76 с |
| Пиковая память процесса Filehub, RSS | 54,3 МиБ |

У тестового MP4 на 96 МиБ локальная SHA‑256 заняла 0,93 с. Передача, обрыв и
завершение вместе заняли 7,77 с. Сервер подтвердил 24 МиБ в момент обрыва.
Клиент продолжил с этого места без повторных байтов. Итоговая SHA‑256 совпала.
Три файла по 16 МиБ загрузились за 4,14 с последовательно и 2,59 с параллельно.

Это локальный профиль: миниатюры и OCR для настоящих снимков, браузерная
отрисовка, Wi‑Fi и другие диски могут дать иные результаты. Текущую очередь
веба с максимумом три одновременные передачи сохраняем. Проверка блоков
TUS не дала бы экономии на этом обрыве. Физическое объединение дублей
потребовало бы отдельной проверки резервного копирования и восстановления.
