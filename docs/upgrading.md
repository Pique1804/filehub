# Обновление существующего Filehub

## Обновить только приложение Android

Скачайте подписанный APK и парный `filehub-<версия>-app.json` из одного
[выпуска FileHub](https://github.com/Pique1804/filehub/releases). В готовом
Linux-пакете и в исходниках есть помощник `server/scripts/publish-android.py`.
На сервере с FileHub запустите его из распакованного пакета. Подставьте
имена двух скачанных файлов.

```sh
sudo python3 server/scripts/publish-android.py \
  --apk filehub-ВЕРСИЯ.apk --manifest filehub-ВЕРСИЯ-app.json
```

Для именованной Linux-установки или Proxmox передайте `--app-dir` со значением
`app_dir` из каталога конфигурации `/etc/ИМЯ.json` внутри машины или LXC,
где работает FileHub. Помощнику нужны `apksigner` и `aapt`. Он проверяет
подпись издателя, хеш, имя Android-пакета и повышение `versionCode`, затем
заменяет APK и манифест вместе. Сервер продолжает работать. Для
[Compose](compose.md#сервер-и-android-при-обновлении) APK обновляется
вместе с образом.

После публикации на вашем сервере новый APK доступен в вебе, а установленный
Android предложит обновление при следующей проверке. Администратор размещает
APK из того же выпуска. Пользователям Android достаточно доступа к своему FileHub.

## С Linux-пакетов 1.40.20 и 1.40.21 на 1.40.22

Скачайте архив и SHA-256 из [выпуска 1.40.22](https://github.com/Pique1804/filehub/releases/tag/v1.40.22). Проверьте сумму
и распакуйте архив на сервере с FileHub. Понадобится закрытая папка для копии
базы и заменяемых файлов. Используйте новый путь для каждого обновления.

```sh
sudo install -d -m 0700 /var/lib/filehub-upgrades
sudo ./install.sh --upgrade plan --backup /var/lib/filehub-upgrades/before-1.40.22
sudo ./install.sh --upgrade apply --backup /var/lib/filehub-upgrades/before-1.40.22
```

Установщик показывает ожидаемый остаток места и проверяет сервер перед
возвратом веб-доступа. Если новый сервер не запускается, установщик пытается
вернуть прежние файлы и базу. Сверьте вход в веб, наличие дисков и файлов и
версию приложения в боковом меню. Если для установки использовалось
нестандартное имя службы, передайте его одинаковым `--name` в обе команды.

## С Linux-пакета 1.40.1 на 1.40.20

Для настроенной установки из готового Linux-пакета **1.40.1** используйте режим
`--upgrade` из сохранённого архива 1.40.20.
Проверьте контрольную сумму архива и распакуйте его, как в [инструкции](installation.md).
Команды выполняются из распакованного каталога на сервере с FileHub.

```sh
sudo install -d -m 700 /var/lib/filehub-upgrades
sudo ./install.sh --upgrade plan --backup /var/lib/filehub-upgrades/before-1.40.20
sudo ./install.sh --upgrade apply --backup /var/lib/filehub-upgrades/before-1.40.20
```

Для именованной установки добавьте `--name ИМЯ` в обе команды. Каталог копии
должен быть новым, а его закрытый родительский каталог должен находиться вне
состояния FileHub и всех доступных в нём источников. План проверяет исходный
выпуск и показывает запас места. Запускайте `apply` в окно без передач файлов.

Обновление сохраняет конфигурацию мастера, аккаунты, сеансы и расположение
оригиналов. Оно заменяет сервер и подписанный APK, временно останавливает веб
и создаёт закрытый согласованный снимок SQLite для восстановления при сбое
запуска. После открытия веб-доступа аварийное восстановление из снимка требует
отдельного решения с учётом записей, созданных после обновления.

Для Docker Compose используйте [обновление Compose](compose.md#сервер-и-android-при-обновлении).

## Прежняя установка 1.40 с прямым запуском Go

Для прежней установки **1.40 с прямым запуском Go через systemd** есть отдельный
[инструмент обновления](../server/scripts/upgrade-ready.py) до **1.40.1**.
Он использует готовые сервер и подписанный APK; сборка не требуется.
Обновление установок с Python-мастером этим инструментом не поддерживается:
он распознаёт их и останавливается до изменений.

## Сначала проверить план

Возьмите ранее сохранённый архив Linux x86‑64 версии 1.40.1
и сверьте его с сохранённым файлом SHA-256. Распакуйте архив и сохраните
`upgrade-ready.py` из этого репозитория рядом с ним. Нужны Python 3.11+ и systemd.
Команды выполняются **внутри машины с Filehub**, для LXC — внутри его Console,
а не в Shell узла Proxmox.

```sh
sudo python3 ./upgrade-ready.py plan --release-dir /absolute/path/to/filehub
```

Без указания `--service` выбирается `filehub.service`. Режим `plan` проверяет
именно запущенную службу, её конфигурацию, доступность хранилищ, версию и точные
хеши опубликованных сервера и APK. Он печатает список заменяемых файлов и хеш
текущего сервера. Служба продолжает работать; файлов данных он не меняет.

## Обновить

Убедитесь, что есть независимая резервная копия оригиналов. Выберите короткое
окно без загрузок и редактирования: Filehub будет недоступен на время остановки,
копирования базы и запуска. Передачи с докачкой могут потребовать повтора.

Подставьте хеш из плана и **новый** каталог резервной копии вне всех источников
Filehub. Например, `/var/lib/filehub-upgrades` подходит, если этот каталог не
входит ни в один источник. Не используйте папку на диске, целиком открытом
в Filehub: копия содержит приватные данные входа и настройки.

```sh
sudo install -d -m 700 /var/lib/filehub-upgrades
sudo python3 ./upgrade-ready.py apply \
  --release-dir /absolute/path/to/filehub \
  --expect-current-sha256 HASH_FROM_PLAN \
  --backup /var/lib/filehub-upgrades/before-1.40.1
```

Инструмент сохраняет прежние файлы программы и приватную конфигурацию,
останавливает только выбранную службу, делает согласованную копию SQLite
с `quick_check`, заменяет программу и APK атомарно и запускает службу.
После запуска он проверяет веб-страницу, отказ анонимному доступу к приватному
API, хеш запущенного сервера, неизменность конфигурации и пользовательских записей.
Служебные метаданные фото, поисковые индексы и кэш хешей могут обновляться в фоне.
При ошибке после остановки он пытается вернуть прежние файлы и запустить службу.
Резервная копия и журнал остаются для оператора даже при неуспешном обновлении.

Не меняются пароли, ключ сессий, имена источников, пути фотографий, оригиналы,
права на дисках, unit-файлы, монтирования и расписание резервирования.
CLIP, Docker, nginx и дополнительные пакеты не устанавливаются.
При параллельных изменениях базы проверка может прервать обновление и вернуть
прежнюю программу; уже записанные новые данные при этом сохраняются.

## Откатить программу

```sh
sudo python3 ./upgrade-ready.py rollback \
  --backup /var/lib/filehub-upgrades/before-1.40.1
```

Откат возвращает прежний сервер и APK, **сохраняя текущую базу и новые файлы**.
Это проверено для пары 1.40 ↔ 1.40.1. Он не переносит старый снимок SQLite поверх
новых загрузок, изменений пароля или альбомов. Другие пары версий требуют
отдельной проверки. Ручное восстановление `index.db` нужно только для аварии
базы: остановите Filehub, сохраните нынешнюю базу вместе с WAL/SHM и восстанавливайте
согласованный снимок с учётом изменений после его создания.

Приватный каталог содержит `transaction.json`, `index.db`, прежние артефакты,
копии конфигурации и результаты проверки. Не публикуйте его и не добавляйте
в Git.

## Хранение точек отката программы

Для обычной выкладки с совместимой базой сохраняйте файлы программы, которые
заменяются при обновлении. Снимок SQLite нужен для миграций, где отдельно
предусмотрено восстановление базы.

[Управление точками отката](../server/scripts/rollback-retention.py) сохраняет
три проверенные точки программы, начиная с той, которая возвращает предыдущую
версию установленной сборки. Если подтверждённой точки для запущенной сборки
нет, очистка остановится. Снимки SQLite, копии конфигурации и записи
неуспешных обновлений остаются в приватном каталоге.

```sh
sudo python3 ./rollback-retention.py plan --root /var/lib/filehub-upgrades
```

План показывает сохраняемые точки, кандидатов на очистку и прогноз свободного
места после создания следующей копии. По умолчанию взят размер копии
установленных программы и APK. Если известен объём конкретной выкладки,
передайте его в байтах через `--incoming-bytes`. В `upgrade-ready.py` поля
`spaceForecast` учитывают логический размер снимка SQLite вместе с данными
WAL, копии программы и временные файлы при замене на каждом томе.

После проверки плана оператор может выполнить `apply` с теми же путями и
`--expect-plan` со значением поля `planId`. Если список точек изменился,
программа попросит сформировать новый план.
Для ежедневной очистки установите помощник в
`/usr/local/sbin/filehub-rollback-retention` и включите
[таймер](../server/distribution/filehub-rollback-retention.timer) вместе с
[его службой](../server/distribution/filehub-rollback-retention.service).
Таймер и ручной запуск используют блокировку обновлений FileHub. Включайте
очистку после проверки отката и согласования правил хранения.

## Проверенный сценарий

На тестовом экземпляре прошли перенос состояния с 1.40 на 1.40.1 и откат.
Сеанс, исходные файлы и расположение хранилищ сохранились. Отдельно проверены
сбой запуска, ошибка копирования базы и повреждённая копия отката.
