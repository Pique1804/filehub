# Filehub Storage на Linux-хосте

Готовый установщик автоматически устанавливает этот сервис на обычном Linux.
Он выполняет привилегированные операции; Filehub работает от отдельного
пользователя. Сетевого API у сервиса нет: только Unix-сокет с проверкой UID.
Монтирование из браузера требует администратора, включая первый запуск,
и CSRF. Произвольные shell-команды/опции от клиента не принимаются.

## Proxmox LXC

Из готового архива на хосте: `sudo ./install.sh --proxmox CTID --restart`.
Из checkout для уже установленного Filehub:

```sh
sudo python3 server/host-storage/proxmox.py --ctid CTID --restart
```

Адаптер сохраняет конфигурацию CT и предыдущий код/службы, вычисляет UID/GID
через реальные карты контейнера, устанавливает отдельный host-сервис, передаёт
постоянный каталог сокета и выделенный каталог дисков. Новые bind-монтирования
могут потребовать перезапуска выбранного контейнера; `--restart` разрешает его.
Оригиналы и базу адаптер не удаляет. Конфигурации других CT не переписываются.

Диски передаются рекурсивным LXC bind, чтобы уже подключённые вложенные
файловые системы возвращались после загрузки CT. Отдельная служба готовит
shared-поддерево; общая propagation корня хоста не меняется. Каталог сокета
постоянный, поэтому перезапуск host-сервиса не оставляет CT со старым inode.
Контейнер не получает block devices, CAP_SYS_ADMIN хоста или инфраструктурные
SSH-ключи. Идентичность файловой системы сверяется с mountinfo на обеих сторонах.

`--allow-uuid UUID` ограничивает сервис выбранными устройствами. При повторной
установке ранее заданный фильтр сохраняется. Loop-устройства по умолчанию
запрещены; `--allow-loop` работает только вместе с явным списком UUID и нужен
для изолированной приёмки, а не для доступа к rootfs соседних контейнеров.

## Ручное подключение службы дисков

Эта процедура подходит для уже установленного FileHub, если администратор
подключает службу отдельно.

Если у вас остался отдельный комплект 1.40.20, подготовьте файлы
`filehub-1.40.20-connect-host.sh`, `filehub-1.40.20-host-tools.tar.gz`,
`filehub-1.40.20-host-tools.tar.gz.sig` и `filehub-host-tools-publisher.pem`.
Для новой установки используйте готовый Linux-пакет из [текущего выпуска](https://github.com/Pique1804/filehub/releases/latest).

Сверьте SHA-256 открытого ключа издателя с закреплённым здесь отпечатком.
Команда рассчитывает его по DER-представлению открытого ключа (SPKI).

```sh
openssl pkey -pubin -in filehub-host-tools-publisher.pem -outform DER | sha256sum
```

Ожидаемый отпечаток — `a657f039f1650bc59b39dade02c2804586891a5d5ed65341ff6ae7ff242aeab2`.
Для Proxmox запустите команду на узле. Замените `CTID` на номер контейнера,
а `NAME` на имя установки (по умолчанию `filehub-onboarding`).

```sh
sudo bash filehub-1.40.20-connect-host.sh filehub-host-tools-publisher.pem \
  filehub-1.40.20-host-tools.tar.gz filehub-1.40.20-host-tools.tar.gz.sig \
  --ctid CTID --name NAME --restart
```

На обычном Linux используйте `--linux --name NAME --restart` вместо `--ctid CTID`.
Утилита проверяет подпись архивных байтов до распаковки. Установку из доверенной
полной копии выпуска можно по-прежнему выполнить через `install.sh`.

## Операции

`lsblk` перечисляет готовые файловые системы. Подключение идёт по UUID
с `nodev,nosuid,noexec`; FAT/exFAT/NTFS дополнительно получают UID/GID приложения.
Создаётся только новая папка `Filehub`. Существующие владельцы, права и файлы
не меняются. Реестр UUID сохраняется перед mount и читается при перезапуске;
исчезнувшие устройства остаются зарегистрированными для повторного подключения.

Системные устройства и их соседние разделы, чужие точки монтирования,
повторные UUID, readonly, шифрование, RAID/LVM и неподдерживаемые файловые
системы не подключаются. Уже смонтированную ОС папку можно предоставить как
источник; сервис не перемонтирует её. Форматирования, удаления, force/lazy umount
и автоматической переразметки в API нет. Пустой диск требует отдельной подготовки
в ОС с осознанным выбором файловой системы; Filehub это не делает скрытно.

## Служба и ресурсы

`install.py` создаёт root-службу, каталог монтирований, закрытый сокет и реестр
UUID. `install.sh` — её оболочка. `--update` сохраняет предыдущий код/юнит
в `/var/backups`. Прямой запуск для существующего аккаунта:

```sh
sudo bash server/host-storage/install.sh --user filehub
```

Предел сервиса — 96 МиБ RAM, swap0, 25% CPU. Нельзя добавлять `PrivateMounts`,
`PrivateTmp` или `Protect*`, которые создают отдельное пространство монтирований:
новые mount должны быть видны приложению. Защита основана на фиксированном
наборе операций, UID сокета, UUID/проверках точек монтирования и ограниченных capability.

Приёмка прошла с настоящим kernel mount ext4 нового файла-образа, загрузкой PNG
из браузера на смонтированный диск, перезагрузкой CT и восстановлением после
umount. Дополнительно проверены pure-Python запреты и повторные shared-пути,
чтобы сервис не накладывал mount повторно. Физические USB-контроллеры и все
заявленные файловые системы по отдельности не испытывались.

Основа: [shared subtrees Linux](https://www.kernel.org/doc/Documentation/filesystems/sharedsubtree.txt),
[mount(8)](https://man7.org/linux/man-pages/man8/mount.8.html).
